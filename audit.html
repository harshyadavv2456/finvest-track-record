FinVest Audit

Independent, read-only audit of FinVest (harshyadavv2456/finvest-app @ c3dcad0, API finvest-api-gwkz.onrender.com) performed 2026-10-01 IST. Nothing in FinVest was modified. Counts below are audit evidence, not a stock list.

0. Summary of findings

  • Pipeline reliability is excellent: 30/30 of the last 30 daily-refresh.yml runs succeeded (29 scheduled + 1 manual), every job in every run succeeded. Typical run takes 2.75 h (min 2.55, max 3.34).
  • The schedule is not 06:00 IST in practice. GitHub starts the cron late: mean delay 298 min (max 909 min). Runs finish between ~11:30 and 14:20 IST (mean 12.92 h IST, max 14.2). A 14:30 IST fetch is usually, but not always, safe.
  • Diagnosis for why FinVest’s own tracking never updates: CONFIRMED, with refinements (section 5).
  • as_of_date is the run date, not the price date (section 3). For India, the stock payload's price_date is one calendar day earlier than the true bar date, and prices are 1–2 sessions behind as_of_date.
  • API has no history: every endpoint serves only the latest snapshot; the by-intent screener is capped at 200 per call (AVOID lists hit the cap), so the full universe must be pulled through /stocks/{market} + /stock/{ticker} (done here).
  • No verifiable historical signals exist; no backfill was done (section 7).
  • Today the model is almost entirely AVOID (India 769/844, US 482/611) with only 5/8 long signals and zero ADD/REDUCE/EXIT: the INITIATE/ADD book will be tiny and concentrated. Every stock in each market also carries the same market regime label (all “recovery” in IN, all “accumulation” in US).

2. Live data: fields, intents, conviction scale, counts

Endpoints used (all unauthenticated, 200 OK): /api/health, /api/coverage, /api/system/status, /api/intelligence/stocks/{IN|US} (list of tickers: IN 844, US 611, no duplicates), /api/intelligence/stock/{ticker} (full record), /api/intelligence/screeners/by-intent/{INTENT}?market=&limit=200 (limit max 200, returns only ticker/market/intent/conviction/asset_regime/cvar_95/last_price/rationale), /api/top-opportunities/{market}, /api/ticker/{t}/daily (≈1100–2500 OHLCV rows, 4 s warm).

3. How as_of_date relates to the last price bar

  • as_of_date = date.today() on the GitHub runner (quant_system/run_full_daily_intelligence.py lines 1298 & 2089), i.e. the UTC run date, not the date of the last price. Intelligence was generated 2026-09-30 13:52 IST for as_of_date 2026-09-30.
  • US: price_date 2026-09-29 for 600/611 stocks = the last completed US close, 1 session behind as_of_date. last_price matched Yahoo close exactly (600/600 within 1%).
  • India: price_date is the UTC date of a midnight-IST timestamp, so it is one day early: shifting by +1 day matches Yahoo closes for 811/828 stocks (within 0.1%). True bar dates: 437 stocks on the 2026-09-29 close, 393 on 2026-09-28 — a mixed 1–2 session lag. Example: a stock whose last_price equals the 28-Sep close shows price_date 2026-09-27.
  • FinVest’s /api/ticker/{t}/daily carries an unfinished bar with close=null for the most recent session on India tickers (the row for “2026-09-29” has Yahoo’s 30-Sep open and no close). Closes for all earlier dates match Yahoo exactly (max diff 0.0 across 500 overlapping days for RELIANCE, TCS, CHOICEIN, AAPL, NVDA, GNRC).
  • 11 Indian and 9 US scored tickers have no Yahoo history at all (delisted/renamed: e.g. TATAMOTORS.NS, LTIM.NS, K, MMC); 14 IN and 11 US have price dates months or years old (one currently long-rated Indian name carries a last price dated 2018). These are stale-price signals; this tracker never invents a price: such names are flagged and, if entered, cannot be marked (see Methodology).

Implication for timing: the signal is observable from ≈14:00 IST on its own as_of_date (the run finishes 13:52–14:20 IST, then publishes to R2 and triggers a Render redeploy), not “the day after”. The tracker conservatively uses its own fetch time as the observation time (see Methodology), and the signal’s information is already 1–2 sessions old when observed.

5. Why FinVest’s own tracking never updates — diagnosis verdict: CONFIRMED

  1. Timeline + positions live on Render's ephemeral disk. timeline_api.py:29 → FinSight/public/timeline; position_tracker_api.py:35-41 → FinSight/public/positions. .gitignore:78 ignores FinSight/public/ and :77 FinSight/data/; render.yaml declares no disk: (free plan). Evidence live: /api/timeline/history/IN?days=30 → days_found: 0; /api/positions/active/IN → 0 positions; /api/positions/summary → all zeros. Additionally the workflow ends with a Render redeploy every day (daily-refresh.yml:327-333), which wipes the disk, and the free tier also sleeps/restarts.
  2. No workflow calls the position/timeline writers. grep -rn "sync_positions\|positions/sync\|timeline/save\|save-all\|score_decision_outcomes\|sync_decision_calls" .github/ returns nothing. The only callers are (a) FinSight/daily_refresh_orchestrator.py:276-327,394-395 (step_timeline, step_positions → sync_positions.py) — a retired local orchestrator not referenced by any workflow; (b) front-end buttons: ActivePositionsPage.tsx:105 (POST /api/positions/sync/{market}) and SimulatorPage.tsx:85 (POST /api/timeline/save/{market}) that only run when a visitor opens the page and are lost at the next redeploy.
  3. score_decision_outcomes.py and sync_decision_calls_to_supabase.py are never invoked. The only repo occurrences of those names are their own docstrings and a comment in supabase_schema.sql:153. score_decision_outcomes.py:11-12 claims “Run daily … (see .github/workflows/daily-refresh.yml)” but the workflow contains no such step (it has only sync_intelligence_to_supabase.py, line 233).
  4. Decision-call log is written to a runner-local directory. decision_logger.py:33,102-103 writes FinSight/state/decision_calls/YYYY-MM-DD.jsonl from layer6_decision_engine.py:782-790 during the intelligence job; the job uploads only FinSight/public/intelligence/ as artifact, so the JSONL is destroyed with the runner. Even if sync_decision_calls were scheduled it would find an empty directory on a fresh runner (sync_decision_calls_to_supabase.py:25).
  5. Refinement: sync_intelligence_to_supabase.py does run daily and appends to Supabase intelligence_history with a 90-day prune — this is a potential durable history but it is capped at 90 days, was not used here (Supabase untouched by design), and nothing reads it for performance tracking. The Trust Dashboard / Timeline front-ends read the empty ephemeral stores instead.
  6. Net: FinVest produces a fresh signal set every day but nothing durable stores prior days or scores outcomes, so every “track record” page is empty by construction. That is exactly the gap this project fills.

6. Other things that could distort performance numbers

  • Date/time labelling: as_of_date = UTC run date; India price_date is one day early (§3). Tracking must use observation time (fetch time) and exchange calendars, never as_of_date for pricing.
  • Price lag: signals use prices 1–2 sessions older than observation (§3); India’s partial last bar has null close. Signal-day-open results are therefore a look-ahead variant (labelled theoretical).
  • Survivorship / universe drift: the universe is whatever is scored today (844 IN / 611 US); names drop out silently (delisted/renamed: 11 IN, 9 US in the first snapshot have no Yahoo data). Exits for “dropped from universe” are logged as reason dropped_universe; there is no history to measure what was removed earlier. Today’s universe is also survivor-biased relative to any past date, which is why backfill is not attempted.
  • Stale prices on signals: 14 IN/11 US names have last_price older than 30 days; one long-rated name priced in 2018. A model long signal on a stock whose data is years old is not tradeable evidence — flagged, and unpriceable names are excluded from entries.
  • Non-equity and duplicate listings: 3 BSE mutual-fund-like ids (0P…BO) in IN; US ETFs (in the first snapshot two long-rated names were share classes of the same index fund) → double-counts one exposure. Different tickers are not de-duplicated by this tracker; the effect is shown in the data.
  • Split/dividend adjustment: FinVest’s bars have adj_close == close in sampled tickers (not dividend-adjusted); this tracker uses Yahoo adjusted close/open (adj factor applied to open) and logs any later revisions of cached closes (>0.1%).
  • India holidays: exchange_calendars has no NSE calendar; BSE (XBOM) holiday set is used (identical in practice) and is only populated through 2026-12-31 — beyond that Mon–Fri is assumed and the benchmark bars decide which days exist. Muhurat sessions and ad-hoc closures should be rechecked yearly.
  • Everything-AVOID regime: market_regime is identical for all names in a market, so “hit rate by regime” is effectively one regime until it changes; conviction is not comparable across intents (§2).
  • Render cold starts / partial pulls: a full pull needs ~850 calls; the fetcher requires ≥98% of the listed universe and a unique, fresh as_of_date, or the day is not recorded.
  • Benchmark index data: ^CRSLDX (Nifty 500) verified on Yahoo (bars through 2026-09-30); ^NSEI, SPY, RSP, ^IRX also verified. Index levels are price indices (no dividends) while stocks are total-return adjusted — a small favourable bias to stocks (≈1–1.5%/yr India). Noted, not adjusted.
  • Free-tier drift: Yahoo data is unofficial and can be revised or throttled; every refresh re-downloads the window and logs revisions.

7. Historical (backfill) sources

The Wayback Machine CDX index returned no captures of finvest-api-gwkz.onrender.com/api/intelligence/* or /api/top-opportunities*; the site itself is a client-side SPA whose captures contain no signal data. FinVest’s own history stores are empty (§5), git history of signals is excluded (signals are gitignored). No verifiable dated historical signals were found, so no backfill was performed. Live tracking starts with the first snapshot (as_of 2026-09-30); the first tradeable entry is the next session after observation.
